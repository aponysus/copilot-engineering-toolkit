I'd approach it as a deliberate, incremental engineering investigation rather than asking an agent to document the entire codebase in one enormous pass.

The distinction I'd make is between three kinds of knowledge:

1. Implementation knowledge: What the source code demonstrably does.
2. Behavioral knowledge: What the deployed system actually does under specific conditions.
3. Business knowledge: Why those calculations and rules exist, and whether their results are financially correct.

Static analysis can establish much of the first. Your VDI work can substantially strengthen the second. Some of the third will still require domain experts, specifications, or independent accounting rules.

## 1. Overall approach

A two-stage documentation program

Stage I — Source archaeology

Start now

Systems Investigator traces code and dependencies. Documentation agent builds the reference. Independent Reviewer validates important claims.

Output: source-grounded architecture, execution flows, calculation definitions, interfaces, known uncertainties

Stage II — Runtime characterization

Run controlled cases in the Windows VDI, collect inputs/outputs and execution evidence, compare observed behavior to the static model, and investigate discrepancies.

Output: verified behavioral examples, characterization tests, corrected documentation, stronger migration contracts

I would design both stages around a single set of project-owned documentation. The second stage should enrich and correct the first, without creating a separate, competing body of documentation.

## 2. Start by understanding the system's shape

Your first mistake to avoid is asking:

> Document everything about Fund Manager.

An agent will typically produce a plausible-sounding architectural overview, perhaps 30–50 pages, without necessarily having traced enough code to support it.

I'd instead begin with a bounded system reconnaissance.

Have Systems Investigator establish the solution layout, assemblies, application entry points, major services, calculation orchestration, persistence boundaries, configuration, external dependencies, and the relevant test infrastructure.

The key questions I'd want answered initially are:

| Area             | Questions to investigate                                              |
| ---------------- | --------------------------------------------------------------------- |
| Entry points     | What actually starts a calculation? API, job, UI, scheduler, service? |
| Orchestration    | What determines which calculations execute, and in what order?        |
| Domain model     | What are the core entities and relationships?                         |
| Data access      | What is computed in C# versus SQL or external components?             |
| State            | Where is intermediate and final calculation state stored?             |
| Dependency graph | Which calculations depend on other calculations or upstream data?     |
| Configuration    | What determines calculation behavior, dates, options, and modes?      |
| Failure handling | What happens on partial failure, cancellation, or restart?            |
| Testing          | What existing tests, fixtures, and executable examples are available? |

The result should be a navigable map of the system, not an exhaustive explanation yet.

### Why this matters

A calculation engine can have deceptively simple entry points while relying on a substantial network of implicit contracts.

For example, a value might be produced by a C# service that calls a stored procedure, which retrieves a previously materialized result generated by another calculation process.

Without understanding that dependency chain, a documentation agent can easily mistake a lookup for the calculation itself.

I'd explicitly instruct the investigator to distinguish where a value is retrieved, where it is transformed, and where it is originally calculated.

## 3. Use a breadth-first, then depth-first investigation

Once the system map exists, I would split the investigation into bounded work packages.

Pass A — Execution lifecycle

Trace a calculation request from initiation through orchestration, data loading, calculation steps, persistence, and final status or output.

Establish the actual execution sequence, conditional branches, and error paths.

Pass B — Data model and dependencies

Identify the entities, schema relationships, mapping rules, and stored procedure contracts supporting the engine.

Pay particular attention to where data changes meaning or grain.

Pass C — Individual calculations

Investigate calculation families one at a time: their formulas, inputs, dependencies, output semantics, temporal rules, and error behavior.

Pass D — Operational behavior

Investigate caching, concurrency, incremental recalculation, retries, failure recovery, configuration, and environmental assumptions.

Treat any claims that require actual execution as pending runtime verification.

You could parallelize independent calculation investigations later, but I wouldn't parallelize the initial architectural discovery excessively. You want a coherent system model before distributing deeper work.

## 4. Make the calculation catalog the centerpiece

For the Fund Manager calculation engine, I'd invest especially heavily in a calculation catalog.

This might become the most useful and enduring part of the documentation.

Each significant calculation should have a standard structure, something like:

### Example calculation reference

Illustrative structure; not a claim about Parilux's implementation

Calculation: Management Fee Accrual

Business purpose: What financial quantity this calculation is intended to represent, when supported by domain evidence.

Entry points: Methods, services, or execution stages that invoke it.

Inputs: Required data and its sources, grain, units, and temporal interpretation.

Calculation logic: Precise equations, branches, transformations, and aggregation rules traced from source.

Dependencies: Preceding calculations, stored procedures, configuration, or other external data.

Outputs: Values produced, where they're persisted, and subsequent consumers.

Boundary conditions: Zero balances, missing records, period boundaries, exceptions, currency rounding, and other supported cases.

Verification: Existing tests, executable examples, and later observed results.

Unresolved behavior: What is inferred or cannot yet be determined.

For financial calculations specifically, I'd want an agent to investigate several subtle dimensions whenever relevant:

- Effective dates versus posting dates versus valuation dates.
- Period activity versus as-of balances.
- Sign conventions and classification semantics.
- Precision and rounding order.
- Currency conversion rates and timing.
- Aggregation grain and grouping rules.
- Dependencies on prior calculation runs.
- Recalculation after corrections or late-arriving records.

The documentation should use precise mathematical notation where it actually clarifies the implementation, especially for fees, allocations, NAV/P&L, and other numerical formulas.

Importantly, though, a formula inferred from method names is not documentation of a formula. It has to be supported by the actual implementation or a trustworthy external specification.

## 5. Separate the investigator from the document author

I'd use three agent roles, but with clear responsibilities.

| Agent                | Responsibility                                                      | Writes                     |
| -------------------- | ------------------------------------------------------------------- | -------------------------- |
| Systems Investigator | Establish factual behavior from source                              | Scoped investigation notes |
| Documentation        | Convert verified findings into maintainable technical documentation | `docs/`                    |
| Independent Reviewer | Compare important claims against source and flag errors/omissions   | Review findings only       |

I wouldn't have the Documentation agent independently invent missing details or treat the Investigator's report as unquestionable authority.

Instead, it should use the report as navigation guidance and inspect the cited source when necessary.

The Independent Reviewer is especially valuable for calculations whose results could later become migration acceptance criteria.

GitHub Copilot supports separate subagent contexts, which makes bounded investigations practical without filling a single primary conversation with every file and intermediate inference. ## 6. The documentation structure I'd use

I would avoid generating one enormous Markdown file.

Instead, I'd use a small entry-point document and a hierarchy organized around how engineers will search for information.

docs/fund-manager/

Orientation, navigation, scope and known limits

architecture.md

Components, responsibilities and dependencies

execution-lifecycle.md

Calculation orchestration and execution flow

domain-model.md

Entities, identities, relationships and terminology

calculation-catalog.md

Index of individual calculations

calculations/

Calculation-specific technical references

database-contracts.md

Tables, procedures, persistence and external SQL

configuration.md

Runtime settings and behavior switches

operations.md

Build/run, troubleshooting and execution controls

verification.md

How documented behavior has been tested or observed

I'd create these files only as the corresponding findings justify them, preserving any existing project documentation rather than automatically replacing it.

### Include diagrams, but generate them from evidence

Mermaid is a reasonable choice for architecture, sequence, and dependency diagrams because it is text-based and maintainable.

Useful examples include:

- Calculation request lifecycle.
- Major component dependency map.
- Calculation dependency DAG.
- Data flow between C# services, stored procedures, and persistence.
- Important lifecycle state transitions.

A diagram should be a compact representation of documented facts, not an inferred architectural ideal.

### Provenance without bureaucracy

I would not create a giant claims register.

Instead, attach source references directly to consequential documentation: repository-relative file paths, class/method names, and line references where useful. Record the source revision used for the investigation.

Use a compact evidence vocabulary such as:

| Classification    | Meaning                                                     |
| ----------------- | ----------------------------------------------------------- |
| Source-confirmed  | Directly established from source at the documented revision |
| Inferred          | Plausible interpretation based on available evidence        |
| Runtime-confirmed | Observed under a recorded execution scenario                |
| Unresolved        | Cannot be established from available evidence               |

This is particularly important because source-confirmed logic may differ from the code actually deployed, while runtime-confirmed output doesn't necessarily prove the underlying business rule is correct.

## 9. Later: runtime characterization in the Windows VDI

This is where the work becomes especially interesting.

After getting a runnable instance, I would build a repeatable set of characterization experiments.

You aren't merely testing whether the engine produces expected results. You're discovering its behavior.

For each experiment, capture:

| Information                                 | Why it matters                                             |
| ------------------------------------------- | ---------------------------------------------------------- |
| Source revision and binaries                | Establish which implementation was actually run            |
| Database version and relevant configuration | Identify environment-dependent behavior                    |
| Input scenario                              | Make the experiment explainable and potentially repeatable |
| Calculation parameters                      | Capture dates, modes, options, and selected entities       |
| Output values                               | Establish observed behavior                                |
| Relevant logs/traces                        | Correlate outputs with internal execution                  |
| Run outcome                                 | Record success, errors, warnings, or partial results       |
| Comparison with static analysis             | Identify confirmation, contradictions, and gaps            |

I would initially prefer synthetic or explicitly approved test datasets, then progress to representative real data under NT's data-handling controls.

If real client data is used, keep it and any derived outputs within approved corporate systems. Your public GitHub toolkit should never contain Parilux source, client datasets, internal schemas, or confidential findings.

### What experiments I'd run

For each important calculation, devise small controlled cases that isolate a variable.

For instance, if investigating a fee calculation, try cases that distinguish possible interpretations of day counts, rounding sequences, effective dates, and period boundaries.

If investigating transaction aggregation, vary transaction classifications, signs, posting dates, and grouping dimensions one at a time.

If investigating recalculation, compare fresh runs against repeated runs, changes to historical input, and runs following previous failures.

The strongest experiments are those designed to distinguish competing hypotheses.

If two plausible formulas produce the same answer for a normal dataset, that dataset tells you almost nothing about which formula is implemented. Construct an input where their answers differ.

This is where a reasoning model becomes particularly useful: it can derive discriminating test cases from the competing implementations or hypotheses uncovered during static analysis.

## 10. Build a golden-master/characterization test suite

Once the VDI can execute the engine reliably, I'd try to establish a controlled reference dataset and outputs.

The basic pattern is:

Controlled inputs

Parilux engine

Reference outputs

Compare later runs or replacement implementations against the captured behavior, using exact comparisons or justified numerical tolerances.

There are two distinct things to establish:

Behavioral compatibility: A replacement reproduces Parilux's relevant outputs for equivalent inputs.

Financial correctness: Those outputs satisfy independent financial rules, specifications, or reconciled accounting results.

Golden-master tests help establish the first. They do not prove the second, because the original system may contain bugs, undocumented exceptions, or historically accumulated behavior that nobody intended.

This distinction will be extremely important if you eventually pursue the strangler-style modernization and parity testing you've been considering.

The documentation and reference outputs could become the foundation of a much more disciplined migration effort.

## 11. How agents should support runtime investigation

I wouldn't immediately give the agent unrestricted control of the Windows VDI or databases.

Instead, I'd first create a safe, reproducible execution interface.

Ideally, you would be able to invoke calculations with known parameters, collect logs and results, and compare them against captured references without manually navigating the application every time.

An agent could then help with experiment design, fixture creation, output analysis, test generation, and discrepancy investigation.

Over time, the workflow might become:

Systems Investigator identifies a question → Test Engineer designs an experiment → an authorized execution tool runs the scenario → Systems Investigator interprets the observed behavior → Documentation updates the technical reference.

The human remains responsible for deciding which environment operations are permitted and whether the resulting evidence adequately establishes the claimed behavior.

I'd avoid introducing elaborate automation before you have a handful of useful repeatable experiments.

## 12. How to prevent documentation drift

The biggest long-term threat is that the documentation becomes comprehensive but inaccurate after the code evolves.

I'd use three relatively lightweight safeguards.

First, ensure each substantive document references the implementation areas it describes, so a developer can find the relevant code.

Second, link documentation maintenance to behavior-changing work. If an agent changes a documented calculation, it should update the corresponding reference in the same change.

Third, back important claims with executable tests where practical. Tests are usually a stronger long-term defense against behavioral drift than a requirement to manually re-review the entire documentation set.

I wouldn't institute a separate documentation approval board or ongoing manual verification register.

Your broader goal should be a maintained engineering reference whose accuracy is reinforced by ordinary development activity.

## 13. Where I'd start this week

I wouldn't initially tackle the entire Fund Manager engine. I'd establish the workflow with one representative vertical slice.

Given your prior investigation, transaction activity sourcing might be a good candidate, provided it reaches meaningful calculation logic rather than only API mapping.

Have the Systems Investigator trace one representative path end to end. Get the Documentation agent to describe it. Have the Independent Reviewer challenge the documentation.

### The longer-term payoff

You could ultimately end up with three related assets:

- A browsable technical reference describing the Fund Manager engine.
- A set of executable characterization tests establishing observed behavior.
- A catalog of calculation contracts, dependencies, and invariants suitable for guiding a future replacement.

That combination is considerably more valuable than source-generated documentation alone.

The most important principle I'd carry through the entire effort is this: documentation should become progressively more authoritative as evidence accumulates, without ever concealing what remains unknown.

Static analysis establishes the initial model. Runtime experiments test that model. Independent financial rules evaluate whether the behavior is actually correct.

If you maintain those distinctions, the result could be both a useful immediate reference for maintaining Parilux and a substantial foundation for eventually modernizing the calculation engine.
